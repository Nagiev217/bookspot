# Expo + iOS-симулятор — универсальный playbook

Общая инструкция для любого Expo-проекта (React Native): как запускать
приложение в iOS-симуляторе и на какие типовые баги натыкаешься почти
всегда. Ни одного упоминания конкретного проекта — можно класть в любой
новый репозиторий как `docs/ios-simulator-guide.md` и просто дополнять
своими находками по ходу разработки.

---

## Как запускать (день в день)

```bash
cd <путь-до-папки-с-package.json>   # обычно apps/mobile или корень проекта
npx expo start --tunnel      # надёжнее на разных сетях/NAT
# или без --tunnel в общей Wi-Fi сети — быстрее и надёжнее
```

После правок в `babel.config.js`, `metro.config.js` или в зависимостях
(`package.json`) — **обязательно** с `--clear`:

```bash
npx expo start --tunnel --clear
```

Без `--clear` Metro (сборщик JS-бандла) отдаёт старую закэшированную
трансформацию — код на экране визуально "не меняется", хотя файл на диске
уже правильный. Почти всегда, когда правки "не применяются" без видимой
причины — это кэш, а не баг в коде.

Полная нативная пересборка (после изменений в `app.json`/`app.config.js`,
добавления нового нативного модуля, после `expo prebuild`, после смены
bundle identifier):

```bash
npm run ios       # = expo run:ios
npm run android   # = expo run:android
```

## Баг №1 — проект лежит в папке, синхронизируемой iCloud (или Dropbox/Google Drive)

**Самая частая корневая причина непонятных сборочных ошибок.** Если папка
проекта лежит внутри `~/Documents`, `~/Desktop` (при включённой iCloud
"Desktop & Documents Sync") или любой другой облачно-синхронизируемой
папки — происходит следующее:
- файлы читаются с задержкой и иногда с неполным содержимым — Xcode и
  CocoaPods иногда видят "недописанный" файл;
- облачный клиент проставляет на файлы дополнительные расширенные
  атрибуты (у iCloud — `com.apple.macl`, `file-provider-domain-id`),
  которые CocoaPods во время code sign считает посторонним мусором.

Из-за этого корня могут вылезать сразу несколько внешне не связанных
ошибок — см. баги №2 и №3.

**Решение**: держать рабочую копию проекта **вне** любых
облачно-синхронизируемых папок — например в `~/Developer/`,
`~/Projects/`, `~/dev/` — не в `~/Documents/` и не на `~/Desktop/`, если
там включена облачная синхронизация.

**Ловушка**: если случайно оказалось две копии одного репозитория
(например, старая осталась в `~/Documents` после переезда в
`~/Developer`) — это выглядит как "у меня же всё исправлено, а не
работает". См. баг №6.

## Баг №2 — Xcode: "No such module 'Expo'" (или любой другой пакет)

**Симптом**: сборка в Xcode падает с ошибкой отсутствия модуля, хотя
пакет точно стоит в `node_modules` и прописан в `Podfile`.

**Что помогает временно, но не решает корень**: очистка
`~/Library/Developer/Xcode/DerivedData`.

**Частая настоящая причина**: проект в облачно-синхронизируемой папке
(баг №1) — Xcode получает повреждённые/неполные копии сгенерированных
файлов.

**Фикс**: перенести проект в обычную локальную папку, полностью
пересобрать (`rm -rf ios && npx expo prebuild` или `pod install` заново,
затем чистая сборка).

---

## Баг №3 — CocoaPods при code sign: "resource fork, Finder information, or similar detritus not allowed"

**Симптом**: сборка падает на этапе подписи (code signing) именно с этой
фразой в логе.

**Причина**: облачная синхронизация (баг №1) добавляет на файлы
расширенные атрибуты, которые Apple codesign считает "мусором" в файле.

**Фикс**: тот же — вынести проект из синхронизируемой папки.

---

## Баг №4 — диск закончился прямо во время `xcodebuild`

**Симптом**: сборка падает где-то в середине с ошибками нехватки места.

**Причина**: `DerivedData` от прошлых (в том числе неудачных) сборок
копится и может занимать десятки гигабайт.

**Фикс**:
```bash
du -sh ~/Library/Developer/Xcode/DerivedData/*   # посмотреть, что жрёт место
rm -rf ~/Library/Developer/Xcode/DerivedData/*   # почистить (безопасно, пересоберётся)
df -h                                             # проверить, что место освободилось
```

**Правило**: если сборка падает с непонятной ошибкой посередине —
сначала проверить `df -h`, а не сразу лезть в код.

## Баг №5 — приложение крашится сразу при старте после подключения стороннего SDK

**Симптом**: сборка проходит, приложение запускается и сразу падает с
исключением от какого-то стороннего SDK (реклама, аналитика, крэш-репортинг
и т.п.) — например `GADInvalidInitializationException` для Google Mobile
Ads, но паттерн общий для любого SDK с обязательной инициализацией.

**Частая причина**: SDK требует App ID / API-ключ в конфиге
(`app.json`/`app.config.js`, обычно через config-plugin), а его забыли
прописать.

**Фикс**: прописать нужный ID/ключ в конфиге. Если реального ключа ещё
нет (SDK подключается "на будущее") — многие сервисы публикуют официальные
**тестовые ID** специально для разработки (например, у Google AdMob есть
задокументированные публичные test App ID) — использовать их временно,
не боевые, и явно пометить в коде/README, что перед релизом их нужно
заменить на настоящие.

## Баг №6 — "я всё поправил, а в приложении всё ещё старая версия"

**Симптом**: код на диске точно новый (можно `cat`/открыть файл и
убедиться), но в симуляторе рисуется старый экран — будто правки не
сохранились.

**Частая причина**: запущенный `npx expo start` раздаёт бандл из
**другой** копии проекта на диске, не из той, которую редактируете —
например, если случайно есть вторая копия репозитория (см. ловушку в
баге №1), либо Metro был запущен из неправильной рабочей директории в
другом терминале/сессии.

**Как диагностировать, не гадая**:
```bash
ps aux | grep "expo start"
```
В выводе виден **полный путь**, из которого реально запущен процесс —
сразу видно, та это папка или нет.

**Фикс**:
```bash
pkill -9 -f "expo start"
cd <правильная-папка-проекта>
npx expo start --clear
```
Затем перезапустить приложение в симуляторе:
```bash
xcrun simctl terminate booted <bundle.id.вашего.приложения>
xcrun simctl launch booted <bundle.id.вашего.приложения>
```
(или просто закрыть/открыть приложение вручную свайпом и повторным тапом).

**Правило**: если изменения "не применяются" и это не похоже на баг в
самой логике — первым делом проверить, из какой папки реально запущен
Metro, а не подозревать код.

## "Сборка идёт долго, она зависла?"

Первая нативная сборка через Xcode/`expo run:ios` для любого нетривиального
проекта занимает по-настоящему много времени (несколько минут — компиляция
всего нативного кода и всех зависимостей с нуля). Это нормально, не
зависание.

**Как отличить "долго" от "реально зависло"**:
- в терминале, где идёт сборка, должен течь поток логов компиляции — если
  логи появляются (пусть и медленно), процесс жив;
- `ps aux | grep xcodebuild` — процесс должен быть виден и потреблять CPU;
- **после первой** сборки последующие правки JS-кода (без изменений
  нативной части) требуют только `npx expo start` — полная пересборка
  через Xcode не нужна.

## Полезные команды для симулятора

```bash
xcrun simctl list devices | grep Booted           # какой симулятор сейчас запущен
xcrun simctl io booted screenshot out.png         # скриншот текущего экрана
xcrun simctl terminate booted <bundle.id>         # закрыть приложение
xcrun simctl launch booted <bundle.id>            # запустить заново
xcrun simctl listapps booted | grep -B2 CFBundleIdentifier   # найти bundle id установленных приложений
```

## Чек-лист диагностики (если что-то снова сломалось)

1. Из какой папки реально запущен Metro? — `ps aux | grep "expo start"`
2. Проект случайно не в `~/Documents`/`~/Desktop`/другой
   облачно-синхронизируемой папке? — если да, перенести в обычную
   локальную папку (`~/Developer`, `~/Projects` и т.п.).
3. Хватает ли места на диске? — `df -h`
4. Правили `babel.config.js`, `metro.config.js` или зависимости? —
   перезапустить с `--clear`.
5. Ошибка про code sign / "detritus" / "resource fork"? — почти наверняка
   снова облачная синхронизация (баг №1).
6. Краш сразу при старте с исключением от стороннего SDK — проверить,
   настроены ли для него App ID/ключи в конфиге.
