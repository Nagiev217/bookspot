# Продуктовая концепция: маркетплейс услуг + онлайн-бронирование (Азербайджан)

**Рабочее название:** BookSpot (пример; финальное имя — отдельная задача на брендинг)
**Рынок:** Азербайджан, старт — Баку
**Ядро ценности:** «Найди свободное время, а не просто салон» ↔ «Заполни расписание, а не просто получи заявку»

---

## 1. Product structure

**Одно мобильное приложение (iOS/Android) для всех, кроме команды платформы**, плюс отдельная веб-админка для платформы:

| Компонент | Платформа | Аудитория |
|---|---|---|
| Единое приложение (Client + Business + Staff режимы) | iOS / Android (React Native или Flutter) | Клиенты, владельцы бизнеса, администраторы салонов, мастера |
| Admin Panel | Web | Команда платформы (внутренняя, клиентам не видна) |

**Как это устроено внутри одного приложения:**

Пользователь входит по номеру телефона. Если у аккаунта есть роль `BUSINESS_OWNER`, `STAFF` или `ADMIN_STAFF` (менеджер салона) — в приложении появляется переключатель режима, например в профиле:

```
[ Client mode ]  ⇄  [ Business mode ]
```

- **Client mode** — тот самый пользовательский опыт: Home, Search, Bookings, Favorites, Profile.
- **Business mode** — открывает дашборд салона прямо в том же приложении: Dashboard, Calendar, Clients, Services, Masters, Analytics, Settings.
- Один и тот же человек может быть одновременно клиентом (записывается в барбершоп напротив) и владельцем своего салона — переключение мгновенное, без выхода из аккаунта.
- Мастер без прав владельца, войдя в Business mode, видит урезанную версию — только свой календарь и свои брони (без доступа к финансам/настройкам бизнеса).

Технически это не два разных приложения, а один и тот же клиент с разными экранными графами (navigation stack) в зависимости от активной роли — код, стили и компоненты переиспользуются, что также ускоряет разработку MVP.

Всё это работает через единый API и единую базу данных с разделением доступа по ролям (RBAC).

**Ключевые доменные сущности:** User, Business, Branch, Master (Staff), Service, Schedule, Booking, Review, Subscription, Payment, Notification.

## 2. User flow (клиент)

1. **Онбординг** — регистрация по номеру телефона (SMS-код, привычно для рынка AZ) → выбор языка (AZ/RU/EN) → геолокация/город.
2. **Home** — категории, «Available today», «Last minute», рекомендации.
3. **Поиск / фильтры** — по категории, району, дате-времени, цене, рейтингу → список бизнесов/мастеров с бейджем «Свободно сегодня в 18:30».
4. **Страница бизнеса → страница мастера** — просмотр портфолио, отзывов, услуг.
5. **Booking flow** — услуга → мастер → дата → время → подтверждение (+ депозит, если требуется) → оплата (если применимо) → бронь создана.
6. **Уведомления** — подтверждение, напоминания, изменения.
7. **Посещение** — клиент приходит, услуга оказана.
8. **Пост-визит** — запрос отзыва, начисление в историю, предложение повторной записи.

Критический путь для конверсии — шаги 3→5: чем меньше кликов от «хочу сегодня подстричься» до подтверждённой брони, тем выше retention.

---

## 3. Business flow

1. **Регистрация бизнеса** — заявка (название, категория, адрес, документы при необходимости) → модерация админом → активация.
2. **Настройка профиля** — фото, описание, часы работы, филиалы.
3. **Настройка услуг** — название, цена, длительность, категория, привязка к мастерам.
4. **Добавление мастеров** — профиль, специализация, портфолио, персональное расписание.
5. **Расписание** — рабочие часы по дням, перерывы, выходные, блокировки дат.
6. **Приём бронирований** — автоматически через слоты + ручное создание админом (звонок, walk-in).
7. **Управление днём** — календарь, изменение/отмена/перенос.
8. **Аналитика** — выручка, загрузка, no-show, популярные услуги/мастера.
9. **Монетизация платформы** — выбор тарифа, опционально включение комиссии/депозита/продвижения.

## 6. API-архитектура

REST API (JSON), версионирование `/api/v1/`. Аутентификация — JWT (access + refresh), роль передаётся в токене.

**Группы эндпоинтов:**

- `POST /auth/otp/request`, `POST /auth/otp/verify`, `POST /auth/refresh`
- `GET /categories`
- `GET /businesses`, `GET /businesses/:id`, `GET /businesses/:id/services`, `GET /businesses/:id/masters`
- `GET /masters/:id`, `GET /masters/:id/availability?date=&service_id=`
- `GET /availability/search` — сложный поиск «свободно сегодня» по нескольким бизнесам сразу
- `POST /bookings`, `GET /bookings/:id`, `PATCH /bookings/:id` (перенос/отмена), `GET /users/me/bookings`
- `POST /reviews`, `GET /businesses/:id/reviews`
- `POST /favorites`, `DELETE /favorites/:id`
- **Business-side:** `POST/PATCH /business/services`, `/business/masters`, `/business/schedules`, `/business/branches`, `GET /business/calendar`, `GET /business/analytics`
- **Admin:** `PATCH /admin/businesses/:id/status`, `GET /admin/reports`, `PATCH /admin/subscriptions/:id`
- **Webhooks:** платёжный провайдер → `/webhooks/payments`, SMS-провайдер → статус доставки

Для мобильного клиента критичен единый эндпоинт `GET /availability/search`, который возвращает уже отфильтрованные по реальной занятости результаты — вся тяжёлая логика слотов считается на backend, а не на клиенте.

## 7. Логика бронирования (ядро системы)

Это самая критичная с технической точки зрения часть продукта — при ошибке здесь бизнес теряет доверие клиентов.

**Генерация свободных слотов** для пары (мастер, услуга, дата):

1. Взять рабочие часы мастера на этот день (`schedules` + `schedule_exceptions`, если есть переопределение).
2. Вычесть перерывы и заблокированные интервалы.
3. Вычесть уже существующие `bookings` со статусом `confirmed/pending` для этого мастера в этот день.
4. Разбить оставшиеся интервалы на слоты с шагом = `duration_minutes` услуги (с учётом буфера между визитами, если бизнес его задал).
5. Отдать клиенту только те слоты, которые полностью помещаются в свободный интервал.

**Защита от двойного бронирования:**
- На уровне БД — уникальное ограничение/блокировка на пересечение интервалов `(master_id, start_time, end_time)` через транзакцию с `SELECT ... FOR UPDATE` или через optimistic locking с проверкой пересечения перед `INSERT`.
- Короткий TTL-холд слота (например, 3–5 минут) на время, пока клиент проходит шаги подтверждения/оплаты депозита, чтобы два клиента не заняли один слот одновременно.
- Idempotency-key на запрос создания брони — защита от повторной отправки при плохом интернете.

**Статусы брони:** `pending` (ждёт депозит/подтверждение) → `confirmed` → `completed` / `cancelled` / `no_show`. Отмена и перенос — с учётом политики бизнеса (например, «отмена без штрафа за 4 часа до визита»).

## 8. Архитектура монетизации

Три независимых, но совместимых потока:

**1. Подписка бизнеса** (SaaS-модель) — тариф ограничивает: число мастеров, число филиалов, доступ к аналитике, Last Minute, продвижению, автонапоминаниям.

**2. Комиссия с бронирований**, оплаченных через платформу — берётся из `payments` в момент завершения услуги; ставка хранится в `businesses.commission_rate` и может отличаться по тарифу.

**3. Продвижение** — отдельная сущность `promotions` (business_id/master_id, type: search_boost/featured/banner, period, price), обязательный визуальный бейдж «Sponsored».

Технически это разные объекты биллинга, но один и тот же `payments`-модуль обслуживает все три — с полем `type`, чтобы отчётность и финансовая аналитика были едиными.

## 9. MVP roadmap

**Фаза 0 — Fundament (4–6 недель)**
Auth, роли, базовая БД, категории, регистрация бизнеса с модерацией.

**Фаза 1 — Core booking (6–8 недель)**
Услуги, мастера, расписания, генерация слотов, booking flow, «Мои записи», push/SMS-уведомления (подтверждение + напоминание).

**Фаза 2 — Discovery (4 недели)**
Поиск, фильтры, «Available today», страницы бизнеса/мастера, избранное, отзывы.

**Фаза 3 — Business tools (4 недели)**
Календарь для бизнеса, ручное создание/перенос записи, базовая аналитика (записи, выручка, no-show).

**Фаза 4 — Monetization (3–4 недели)**
Тарифы, депозиты, Last Minute, простая комиссия, интеграция с платёжным провайдером (например, локальный эквайринг — Kapital Bank/PASHA Pay и т.п. — уточняется отдельно).

**Фаза 5 — Admin + polish**
Админ-панель, модерация отзывов/жалоб, финальная доработка UX, нагрузочное тестирование booking-логики.

Итого MVP — ориентировочно 5–6 месяцев с небольшой командой (1–2 backend, 1–2 mobile, 1 дизайнер, 1 QA частично). Объединение Client и Business в одно приложение немного увеличивает сложность навигации/состояний в мобильной разработке, но экономит на отдельном веб-дашборде для MVP — фактически лишний фронтенд-стек на старте не нужен, что для небольшой команды выгоднее по срокам.

## 10. UI/UX структура

- **Bottom navigation, Client mode:** Home · Search · Bookings · Favorites · Profile
- **Bottom navigation, Business mode:** Dashboard · Calendar · Clients · Services/Masters · Analytics (Settings — через Profile)
- **Переключатель режима** — в профиле или через long-press/свайп на аватаре в шапке; визуально чётко разводит два режима (например, разный акцентный цвет шапки — нейтральный для Client, тёмный/премиальный для Business), чтобы не путать «где я сейчас».
- Приоритет — минимум шагов до подтверждённой брони (не более 4–5 экранов от Home) в Client mode.
- «Available today» и «Last Minute» — доступны в 1 тап с главного экрана, это главный дифференциатор продукта.
- Состояния бронирования должны быть визуально однозначны (цвет/иконка: pending — жёлтый, confirmed — зелёный, cancelled — серый).
- Push-уведомления должны учитывать активный режим: бизнес-уведомление («новая запись») не должно приходить, пока владелец сидит в Client mode, и наоборот — сообщать об этом стоит независимо от текущего режима, но при открытии из пуша приложение сразу переключается в нужный режим.

## 11. Список экранов (MVP)

Все экраны ниже (кроме Admin) живут в одном мобильном приложении, сгруппированные по режиму.

**Единое приложение — Client mode:** Onboarding/OTP → Home → Category list → Search results → Business profile → Master profile → Service list → Booking: Date → Booking: Time → Booking: Confirm+Deposit → Booking success → My Bookings → Booking detail → Favorites → Reviews (list + create) → Profile/Settings → Notifications.

**Единое приложение — Business mode** (появляется у ролей BUSINESS_OWNER/STAFF после переключателя в профиле): Dashboard → Calendar (day/week) → Booking detail (create/edit) → Services list/edit → Masters list/edit → Master schedule editor → Branches (post-MVP, но заложить в архитектуру) → Analytics → Subscription/Billing → Business settings.

**Экран регистрации бизнеса** — отдельный флоу «Стать партнёром» (доступен из Profile в Client mode: «Добавить свой бизнес»), после одобрения админом открывает Business mode на этом аккаунте.

**Admin (отдельная веб-система):** Login → Businesses list/detail (approve/block) → Users list → Categories editor → Reviews moderation → Reports/complaints → Subscriptions/tariffs → Platform revenue dashboard.

## 12. Дизайн-система

- **Стиль:** минимализм, премиальность, много воздуха, крупные фото карточек бизнеса.
- **Типографика:** один основной геометричный sans-serif с поддержкой азербайджанской кириллицы/латиницы, 2–3 насыщенности (regular/medium/semibold).
- **Скругления:** средние-мягкие (12–16px на карточках, 8px на элементах форм).
- **Цвет:** 1 акцентный цвет + нейтральная шкала серого + отдельный «sponsored»-бейдж с тонким отличающимся оттенком (не кричащий).
- **Компоненты:** карточка бизнеса (фото, имя, рейтинг, бейдж доступности), чип категории, таймлайн-слот-пикер, календарная сетка для бизнеса, пустые состояния (no bookings yet) — дружелюбные, с иллюстрацией/CTA.
- **Анимации:** плавные переходы между шагами booking flow (прогресс-бар из 4–5 точек), лёгкий фидбэк при выборе слота.

Для детальной реализации в коде (палитры, конкретные шрифтовые пары, токены) стоит отдельно проработать через дизайн-гайд для конкретного стека (React Native / Flutter).

## 13. Админ-панель

Ключевые модули: модерация новых бизнесов (approve/reject с причиной), управление категориями (мультиязычные названия), блокировка пользователей/бизнесов за нарушения, модерация отзывов (жалобы → скрытие → разбан), управление тарифами и их лимитами, обзор всех бронирований платформы (для саппорта), финансовый дашборд (revenue по подпискам/комиссии/продвижению), базовая система тикетов поддержки.

Доступ — с гранулярными ролями (Super Admin / Moderator / Support), чтобы не у всей команды был полный доступ к финансам.

---

## 14. Бизнес-дашборд

Главный экран — сводка дня (записи сегодня, ожидаемая выручка, новые клиенты) + быстрый переход в календарь. Календарь поддерживает day/week/month view, drag-and-drop переноса записи (веб), ручное создание брони «по звонку». Отдельные разделы: клиенты (простая CRM — история визитов, частота, потраченная сумма), услуги/мастера/расписания (см. раздел 5), аналитика (графики: выручка по дням, топ-услуги, топ-мастера, no-show rate, загрузка по часам — прямое обоснование для Last Minute).

## 15. Security considerations

- OTP-аутентификация + rate limiting на попытки входа.
- RBAC на уровне API (middleware проверяет роль + принадлежность ресурса — бизнес не может редактировать чужой филиал).
- Транзакционная защита от двойного бронирования (см. раздел 7).
- PCI-совместимость не хранить карточные данные напрямую — только через токенизацию платёжного провайдера.
- Персональные данные (телефон, история визитов) — шифрование в базе для чувствительных полей, соответствие локальным требованиям по защите персональных данных Азербайджана.
- Защита отзывов от накрутки — отзыв доступен только после `booking.status = completed`, привязан к конкретной брони.
- Логирование действий админов (audit log) для модерационных решений (блокировки, одобрения).
- Защита от злоупотребления Last Minute/промо (лимиты на бизнес, антифрод на массовые фейковые брони).

## 16. Scalability plan

- **Мультифилиальность и мультигород** заложены в схему БД с самого начала (`branches` как отдельная сущность, а не поле в `businesses`), даже если MVP разворачивается только в Баку.
- **Горизонтальное масштабирование backend** — stateless API-сервисы за балансировщиком, БД (PostgreSQL) с read-репликами для тяжёлых запросов аналитики/поиска.
- **Поиск и фильтрация** — при росте каталога вынести полнотекстовый/геопространственный поиск в отдельный индекс (например, Elasticsearch/PostGIS), не нагружая основную транзакционную БД.
- **Очереди** — уведомления (SMS/push/email) и генерация слотов для тяжёлых кейсов — через очередь заданий (например, Redis + worker), чтобы не блокировать API запросы.
- **Мультиязычность и мультивалютность** — с самого начала таблицы категорий/услуг хранят переводы (az/ru/en), что упрощает будущую экспансию в другие страны.
- **Аналитика бизнеса** — по мере роста данных перейти на отдельное аналитическое хранилище (data warehouse) вместо прямых запросов к продовой БД.

## Итог

Ядро дифференциации продукта — не каталог, а **реальная доступность времени** («Available today», Last Minute) плюс инструменты для бизнеса, которые монетизируют простаивающие часы. Технически самое критичное место — booking-логика (генерация слотов + защита от двойного бронирования), она должна быть спроектирована и протестирована в первую очередь, до полировки UI. MVP стоит ограничить категорией beauty & personal care и городом Баку, чтобы быстро проверить unit-экономику до расширения.
